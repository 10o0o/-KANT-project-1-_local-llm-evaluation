# 단계별 학습 안내

수행 범위와 최종 기준은 [발제 원문](project-brief.md)이 기준입니다. 이 안내는 원문의 STEP 1~8을 직접 수행하기 위한 길잡이이며 정답 코드나 미리 완성된 실험 양식을 제공하지 않습니다.

## 기본 진행 방식

**사용자 시도 → 현재 코드·결과 확인 → 필요한 설명이나 힌트 → 사용자 수정·실행 → 리뷰** 순서로 진행합니다. AI는 한 번에 다음 작은 작업 하나를 안내합니다. 필요한 파일은 사용자가 해당 단계에서 만들고, 직접 실행한 결과와 자신의 설명을 남깁니다.

환경 준비도 사용자 작업입니다. 원문의 선행 가이드와 Python 3.12·uv 환경을 참고하되, 현재 선택한 WSL2 실행 경로와 Windows 직접 실행 가이드의 차이를 확인합니다. 모델 다운로드·호출을 포함한 모든 실습 명령은 사용자가 실행합니다.

안내할 작업은 아래 네 종류로 구분하고, 해당 STEP과 완료 근거에 연결합니다.

- **발제 필수:** 아래 STEP 1~8의 과제와 기록, 제출·재실행 요건입니다. 현재 단계에서 필요한 근거만 확인합니다.
- **발제 선택·사용자 필수:** 발제의 선택 실습 4개를 모두 수행합니다. 발제 공통 평가에서는 선택이지만, 이 저장소의 개인 학습 완료 조건입니다.
- **사용자 정의 기준:** [요구사항](requirements.md)의 코딩테스트 풀이 목적, 체감 난이도, 코드 제출 규칙과 선정 기준입니다.
- **추가 학습·방법 제안:** AI가 덧붙인 설명과 절차입니다. thinking·capabilities 심층 분석 등을 완료 조건이나 필수 선행 과제로 삼지 않습니다.

## 이번 프로젝트의 사용자 정의 기준

[요구사항](requirements.md)에 따라 최초 생성 Python 코드를 로직 수정 없이 제출하고 두 회차를 모두 평가합니다. **AC이면서 해당 제출에 적용되는 시간 제한의 70% 미만**인 답변을 유효 정답으로 봅니다. 유효 정답률은 유효 정답 수를 모델당 본 실험 20회로 나누며, 호출 실패·코드 미생성도 분모에 포함합니다. 선정 순서는 **유효 정답률 → 설명 정확성 → 모델 응답 속도**이고 일반 AC 비율도 별도 기록합니다.

이는 사용자가 정한 평가 방식이며 발제의 공통 임계값이 아닙니다. 제출 코드 실행 시간과 모델 응답 시간을 구분하고, 발제가 요구하는 호출 성공/시도 수·지표별 유효 n·품질 평가 근거를 별도로 유지합니다. 일부 회차만 수행한 상태를 20회 실험 완료로 표시하지 않습니다. STEP 2의 필수 통과 조건과 확인 방법은 사용 사례에 맞게 정합니다. 발제에 나열된 조건 예시를 모두 독립된 필수 작성란으로 바꾸지 않습니다.

## 환경과 파일 형식

- Python 3.12와 uv를 사용하고 실제 Python·Ollama·주요 패키지 버전, GPU/VRAM, 실행 설정을 기록합니다. 이 저장소의 환경 파일은 사용자가 생성합니다.
- 선행 환경을 이어 쓸 때의 `pyproject.toml`·`uv.lock`과 사용한 Python 버전은 최종 의존성 근거로 남깁니다. 생성 여부와 실행 근거는 [현재 상태](../STATE.md)에서 확인합니다.
- 원본 결과는 JSON·CSV·JSONL 등 다시 읽을 수 있는 형식으로 저장합니다. 특정 스키마나 폴더명은 필수가 아닙니다.
- 질문 ID·실행 ID·모델·회차·입력·설정·원본 답변·성공/오류 상태·워밍업 여부를 연결할 수 있어야 합니다. 저장 형식은 이 목적을 이해한 뒤 사용자가 선택합니다.
- 질문, 평가 기준, 비교표, 보고서도 해당 단계에서 사용자가 작성합니다. README에 통합하거나 별도 문서로 연결할 수 있으며 같은 내용을 중복 작성할 필요는 없습니다.

## 실험에서 유지할 기준

- 서로 다른 로컬 후보 2개를 비교합니다. 같은 모델의 양자화 두 버전은 이 요건을 대신하지 않습니다. 설치된 모델이라는 이유만으로 후보를 자동 확정하지 않습니다.
- 로컬 본 실험은 **2모델 × 10문항 × 2회 = 40회**입니다. 모델당 워밍업 1회씩 **총 2회**를 별도 기록하고 본 집계에서 제외합니다. 연결 확인 연습을 본 실험 실적으로 세지 않습니다.
- Cloud는 미리 선정한 **공통 5문항 × 1회 = 5회**입니다. 비교할 로컬 결과는 기존 40회 중 해당 문항의 두 회차를 모두 사용합니다. Cloud 비교를 위해 별도의 로컬 20회를 더 요구하지 않습니다.
- 동일 PC·동일 질문·입력 자료·지시문·대화 이력 처리·출력 한도를 적용하고 생성 설정을 기록합니다. 맞출 수 없는 모델별 설정 차이는 밝힙니다.
- 모든 시도의 답변 또는 실패를 보존합니다. 재시도·추가 실험은 별도 기록하고 원래 실패를 성공으로 덮어쓰지 않습니다.
- 모델별 성공 수/전체 시도 수와 **지표별 평균에 사용한 유효 건수 n**을 함께 표시합니다. 정상 수신한 낮은 품질 답변도 평가에 포함합니다. 누락값은 0으로 채우지 않고 사유를 남기며, 유효값이 없으면 집계 불가로 표시합니다.
- 품질 점수는 응답의 어느 부분이 기준을 충족하거나 어겼는지 연결합니다. 특정 점수 척도는 강제하지 않습니다.

## 필수 측정과 해석

| 항목 | 원문에서 요구하는 관측·해석 |
| --- | --- |
| 전체 응답 시간 | 요청 직전부터 최종 응답 수신 직후까지 초 단위로 측정. 별도 측정 없이 TTFT라고 부르지 않음 |
| 로딩 시간 | 최종 응답의 `load_duration`을 나노초에서 초로 변환. 워밍업과 본 실험을 구분 |
| 출력 토큰·생성 속도 | `eval_count`와 `eval_duration`을 기록. 생성 속도는 생성 토큰 수 / 생성 구간 시간(초). 필드 누락 또는 생성 시간 0 이하이면 계산하지 않고 사유 기록 |
| VRAM | `client.ps()`에서 해당 모델의 `size_vram` 확인. 바이트/1,048,576은 MiB. 최대값이 아닌 관측 시점 값이며 GPU 없음·측정 불가는 사유 표시 |
| 실행 조건 | 태그·digest·양자화·실제 Context와 설정 기록. `ollama ps`의 CPU/GPU 적재 상태는 GPU 이용률이 아님 |
| Cloud 사용량·비용 | 호출별 상태·응답·시간·입력/출력 토큰·확인한 단가와 비용 기록. 계산한 추정 비용과 실제 사용 내역을 구분 |

Model Card의 최대 Context와 실제 Context, 다운로드 크기와 RAM·VRAM을 구분합니다. 모델별 토큰화가 다를 수 있으므로 tokens/s만으로 품질이나 체감 속도를 판단하지 않습니다. 로컬 장비·전력·관리 비용을 측정하지 않고 총비용을 0원으로 표시하지 않습니다.

## 최종 완료 확인

요구사항 → 질문·평가 항목 → 원본 실행 기록 → 선택·탈락 이유를 연결합니다. 두 로컬 후보 모두 필수 조건을 충족하지 못하면 그 사실을 밝히고 상대적으로 적합한 후보와 실제 도입 가능 여부를 구분합니다. Cloud 결과가 우수하더라도 최종 로컬 후보 선정과 실제 서비스 운영 방식 권고는 따로 작성합니다.

GitHub 저장소 하나에 사용자 코드·환경 정보·질문·원본 기록·품질 평가·비교표·선정 근거를 모읍니다. README를 따라 재실행하고 개인 또는 팀의 확인 근거를 남깁니다. 팀의 모든 구성원은 모델 실행·결과 기록·채점에 참여하고, 질문·평가 기준·최종 선정은 함께 결정합니다. 팀의 본 실험 40회를 분담하며 각자 전체를 중복 수행할 필요는 없습니다. 분담한 경우 참여 내용을 기록합니다. 공개/가상 자료를 사용하고 API 키·모델 가중치·가상환경은 제출하지 않습니다.

작은 평가셋·제한된 장비·실패 사례의 한계를 설명합니다. AI가 만든 예시 답변이나 백업 코드를 실제 실험·사용자 구현 근거로 제출하지 않습니다. 기본 과제 완료와 개인 전체 학습 완료는 별도로 표시합니다. 개인 전체 학습 완료에는 아래 4개 실습의 수행 근거도 필요합니다.

## 발제 선택·사용자 필수

[발제의 선택 범위](project-brief.md#필수선택-범위) 4개를 모두 개인 필수로 수행합니다. 기본 실험과 결과 정리를 마친 뒤 진행하며, 아래 근거는 개인 학습 계획의 완료 기준입니다. 발제 공통 평가표 자체를 변경하지 않습니다.

| 개인 필수 실습 | 남길 수행 근거 |
| --- | --- |
| 세 번째 로컬 모델 비교 | 실제 실행 기록과 기존 후보와의 비교·해석. 공통 입력·조건을 사용하거나 차이를 명시 |
| Transformers 직접 실행 | 사용자 작성 로딩·추론 코드, 환경·설정, 실제 실행 결과 |
| 동일 모델 양자화 비교 | 같은 모델의 양자화 버전 2개를 조건을 맞춰 비교한 VRAM·속도·품질 결과 |
| Sentence Transformers 임베딩 | 문장 → 임베딩 → 코사인 유사도 실행 결과와 의미 해석 |

모델·입력·반복 횟수는 해당 실습을 시작할 때 사용자가 정합니다. 발제에 없는 추가 실행 횟수는 강제하지 않습니다. FP16·8bit·4bit는 예시이며 셋 모두를 비교할 의무는 없습니다. 기본 로컬 40회·워밍업 2회·Cloud 5회와 추가 실험 기록·집계를 구분합니다.

양자화 비교는 서로 다른 모델 비교로 대체하지 않습니다. 임베딩에서는 같은 모델·설정을 사용하고 토큰 ID와 문장 임베딩을 구분하며, 유사도를 사실성 점수로 해석하지 않습니다. 웹 UI·배포·Vector DB·RAG는 이 4개 실습에 포함되지 않습니다. 자세한 내용은 [발제 선택 실습](project-brief.md#선택-실습)을 따릅니다.

## 추가 학습·방법 제안

아래는 이해와 측정을 돕는 제안이며 발제 필수나 개인 완료 조건이 아닙니다.

- Tokenizer·Chat Template의 역할을 자신의 말로 설명해 봅니다. 발제의 학습 주제이지만 STEP 4의 별도 통과 조건은 아닙니다.
- 독립된 질문은 대화 이력을 초기화하는 방법을 권합니다. 발제 필수는 후보 간 동일한 대화 이력 처리와 차이 명시입니다.
- 개인은 같은 기준으로 재검토하고 팀은 교차 확인하는 방법을 쓸 수 있습니다. 발제 필수는 동일 품질 기준·응답 근거와 팀원 모두의 채점 참여입니다.
- VRAM은 답변 직후 모델을 내리기 전에 조회하면 응답과 관측값을 연결하기 쉽습니다. 발제 필수는 해당 모델의 관측 시점 값을 기록하고 별도 측정 없이 최대값이라 하지 않는 것입니다.
- Cloud 실제 사용 내역을 실행 전후로 확인하면 비용을 대조하기 쉽습니다. 발제 필수는 토큰 사용량·실제 단가 기반 추정 비용과 실제 사용 내역을 구분하는 것입니다.
