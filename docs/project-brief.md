## 1. 프로젝트 개요

개인 또는 팀으로 서비스 상황을 정하고, **로컬 LLM 2개를 Ollama로 실행/비교한 뒤 적합한 모델 1개를 선정**합니다. 진행 기간은 **4일**입니다. Cloud API 모델 1개에도 공통 질문 일부를 적용해 실제 운영 방식을 검토합니다.

선정 이유는 모델의 답변과 측정값, 사용 환경을 근거로 설명합니다.

### 이번 프로젝트의 필수/선택 범위

| 구분 | 수행 범위 |
| --- | --- |
| 필수 | 사용 사례와 요구사항 정의, Hugging Face 모델 정보 조사, 로컬 모델 2개 실행, 같은 질문으로 품질/성능 비교, 소규모 Local–Cloud 비교, 모델 선정과 발표 |
| 선택 | 세 번째 로컬 모델 비교, Transformers 직접 실행, 동일 모델의 양자화 버전 비교, Sentence Transformers 임베딩 실습 |
| 공통 환경 | Windows 수업용 노트북, Ollama, VS Code + uv + Python 3.12. 2번 선행 가이드의 실행 환경을 이어서 사용 |
| 산출물 | GitHub 저장소 하나에 실행 코드/환경 정보/실험 기록/비교표/최종 선정 근거를 함께 제출 |

선택 실습은 필수 실험과 결과 정리를 완료한 개인 또는 팀이 진행하며, 필수 완료 기준에 포함하지 않습니다.

### 프로젝트 시작 전 준비

- 프로젝트 전까지 **Lv.1부터 Lv.2 [딥러닝 실전 & 프롬프트 엔지니어링]까지** 학습합니다.
- **1번:** (1) Ollama 선행학습: Windows 설치와 CLI 첫 대화에서 설치/모델 다운로드/CLI 대화/GPU 확인을 완료합니다.
- **2번:** (2) Python으로 Ollama/Luna 호출하기: VS Code + uv에서 VS Code + uv + Python 환경을 준비하고, Ollama/Luna 호출 방법과 전체 응답 시간 측정을 익힙니다.
- 코드의 `QUESTION`과 `MODEL`을 찾고, 질문을 바꾸어 저장/실행한 뒤 답변과 측정값을 설명할 수 있는지 확인합니다.
- 사전 가이드의 공통 모델은 설치/호출 연습용입니다. 프로젝트에서는 실행 가능 조건 안에서 **서로 다른 로컬 후보 2개**를 선정하고 선택 이유를 기록합니다.

### 선행 실습 다음에 할 일

앞의 두 가이드에서 익힌 설치와 Python 호출 방법을 활용합니다. 개인 또는 팀의 사용 사례와 요구사항을 정한 뒤, 같은 질문과 평가 기준으로 모델을 비교합니다.

STEP 1에서 누가 어떤 업무에 사용할 모델인지 한 문장으로 정리하세요. 요구사항과 로컬 후보 2개를 정하고, 평가 질문과 기준을 확정한 뒤 실험합니다. Cloud 모델은 비교 기준으로 활용하고, 최종 모델은 로컬 후보 중에서 선정합니다.

**현재 제공 자료:** 2번 가이드의 단일 Ollama 호출 예제, 단일 Luna 호출 예제, 전체 응답 시간 측정 예제와 해석 예시입니다. 예제는 답변과 측정값을 터미널에 표시합니다. 프로젝트의 반복 실행/추가 측정/결과 파일 저장/품질 평가는 개인 또는 팀이 이 예제를 바탕으로 구성합니다.

AI를 활용한 코드 작성/수정을 허용합니다. 한 질문의 호출과 기록부터 확인한 뒤 반복 실험으로 확장합니다. 수강생은 자신이 사용하는 코드에서 입력/모델/설정/저장 위치를 찾고, 실제 실행 결과와 평가 근거를 설명할 수 있어야 합니다.

# 2. 프로젝트를 통해 무엇을 배우나요?

- **Transformers / PyTorch:** 직접 모델을 로딩하는 선택 실습에서 활용

## 4) Local LLM과 Cloud LLM 비교하기

Cloud API와 로컬 운영의 품질, 비용, 데이터 통제, 운영 부담을 비교합니다.

### Cloud API

- 구축이 비교적 쉬움
- 높은 모델 성능 활용 가능
- 인프라 운영 부담이 적음
- 사용량 기반 비용 발생
- 외부 API 의존
- 데이터 보안 및 개인정보 고려 필요

### Local / Open-source LLM

- 데이터 통제 가능
- 모델 커스터마이징 가능
- 내부망 / Private 환경 구성 가능
- 모델과 요구 성능에 맞는 실행 장비 확보/관리 필요
- 모델 선택 및 서빙 필요
- 운영 난이도가 높음

비교 결과를 바탕으로 서비스 상황에 맞는 운영 방식을 제안합니다.

# 3. 프로젝트를 마치면

답변 품질과 응답 시간, 장비와 운영 조건을 근거로 모델 선택을 설명할 수 있어야 합니다.

## 프로젝트 종료 시 갖게 되는 역량

- Hugging Face에서 필요한 모델을 탐색할 수 있다.
- Model Card를 읽고 모델 특성을 파악할 수 있다.
- License를 확인하고 모델 사용 가능 여부를 판단할 수 있다.
- Ollama와 Python 실행 코드를 연결하여 로컬 모델 2개를 호출하고 결과를 기록할 수 있다.
- 모델별 성능/속도/메모리 사용량 차이를 측정할 수 있다.
- Quantization이 모델 실행에 미치는 영향을 이해할 수 있다.
- 선택 실습을 수행한 경우 Sentence Transformers로 문장 Embedding을 만들고 유사도를 해석할 수 있다.
- Local–Cloud의 실측 결과와 운영 조건을 구분하고, 모델 선택과 실행 위치에 대한 판단을 설명할 수 있다.
- 서비스 요구사항에 따라 적절한 LLM을 선택할 수 있다.

# 4. 기존 강의에서 배운 내용은 어떻게 활용되나요?

Lv.1과 Lv.2 초반에 학습한 내용을 실제 LLM 환경에 적용합니다.

프로젝트 이전까지 학습한 Transformer, Hugging Face, Tokenizer, Chat Template, Model Card, Prompt Engineering, LLM API 호출과 실험 기록을 활용합니다. 기존의 프롬프트 비교 실험을 **질문과 평가 기준을 유지하고 모델을 바꾸는 실험**으로 연결합니다. API 서버 구축, LangChain, RAG는 이후 학습 범위이며 이번 필수 구현에 포함하지 않습니다.

| 기존 학습 내용 | 프로젝트 활용 |
| --- | --- |
| Git & GitHub | 프로젝트 Repository 관리 및 협업 |
| AI Literacy | Closed API와 Open-source LLM 비교 |
| 기초 수학 / 선형대수 | 벡터/유사도 이해, 선택 임베딩 실습의 결과 해석 |
| 딥러닝 기초 | Tensor / GPU / 모델 실행 구조 이해 |
| Transformer | LLM 구조 이해 |
| Tokenizer | 모델별 Tokenization 방식 확인 |
| Hugging Face Transformers | 모델 저장소와 설정 이해, 직접 로딩은 선택 실습 |
| Model Card / License | 모델 특성 및 사용 가능 여부 판단 |
| Chat Template | Chat 모델 입력 형식 이해 |
| Generation Decoding | 모델별 출력 특성 비교 |
| Prompt Engineering | 모델 비교를 위한 동일 Prompt 설계 |
| Structured Output | 필요한 태스크의 출력 형식 검사. 공통적으로 JSON 응답 강제나 Tool Calling/멀티모달 구현을 요구하지 않음 |

### 구현이 막힐 때 참고할 학습 내용

막힌 작업에 해당하는 부분을 찾아 복습하세요. 기존 예제에서 질문과 평가 기준을 유지하고, 비교 대상을 프롬프트 버전에서 모델로 바꾸는 흐름을 생각해 보세요.

- **Python — 09. 파일/pathlib/JSON/JSONL:** 응답과 설정을 딕셔너리로 정리하고 파일에 저장한 뒤 다시 읽는 방법을 참고합니다. 여러 질문을 실행하는 부분은 반복문과 함수 단원을 함께 봅니다.
- **딥러닝 심화 — 6-1강의 Hugging Face Hub와 Model Card/License, 9-5강의 입력 디버깅:** 모델의 용도/언어/라이선스와 입력 길이/출력 한도를 확인할 때 참고합니다. 이번 Ollama 경로에서는 입력 형식과 길이의 의미를 연결해 이해하면 됩니다.
- **딥러닝 실전 & 프롬프트 엔지니어링 — 6장 1강의 Baseline/Few-shot/문제 분해와 평가 루브릭:** 비교 조건 고정, 원본 응답과 실행별 결과 기록, 같은 기준으로 채점하는 방법을 참고합니다.
- **같은 과정 — 10장 1강의 Timeout/Rate Limit/Retry/Fallback, 10장 2강의 token/cost/latency logging:** 실패 처리와 사용량/비용 집계, 미확인 값을 0과 구별하는 방법을 참고합니다.
- **Git & GitHub — 3장 2강의 저장소 구성과 Issue 관리:** README에 환경/실행 방법/결과 파일 위치를 정리할 때 참고합니다.

# 5. 프로젝트 과제

특정 Use Case에 맞는 오픈소스 LLM 후보를 탐색하고, 실행/평가 결과를 바탕으로 모델을 선정합니다.

개인 또는 팀 단위로 하나의 Use Case를 정하고 해당 서비스에 적합한 모델을 탐색합니다. 이번 산출물은 **서비스 상황을 가정한 모델 비교/선정 결과**입니다. 완성형 챗봇, 웹 UI, 웹서버, 배포, Vector DB/검색/RAG 구현은 필수 산출물에 포함하지 않습니다.

문서 요약이나 문서 질의응답을 선택한 개인 또는 팀은 공개/가상 문서를 프롬프트에 직접 제공하는 범위로 수행할 수 있습니다.

### Use Case 예시

- 고객 상담 챗봇
- 사내 문서 요약
- 개발자 Coding Assistant
- 한국어 질의응답
- 문서 분류
- 뉴스 요약
- 교육용 AI Tutor
- 개인 업무 Assistant

# 6. 프로젝트 전체 프로세스

필수 과정은 **STEP 1부터 STEP 8까지**입니다. 양자화/임베딩은 별도의 선택 실습으로 표시합니다.

> **문제 정의 → 요구사항 정의 → 모델 탐색 → 실행 환경 확인 → 평가 질문 확정 → 로컬 비교 실험 → 소규모 Cloud 비교 → 최종 모델 선정**
> 

선택 실습 A/B 및 추가 모델/Transformers 실행은 필수 결과를 확보한 뒤 진행합니다. 기본 진행에서는 STEP 6을 마친 뒤 STEP 7의 Cloud 비교로 이동합니다.

### 4일 진행 안내

| 일차 | 주요 작업 | 확인할 결과 |
| --- | --- | --- |
| 1일차 | 사용 사례/요구사항 정의, 후보 모델 2개 조사, 2번 예제로 모델별 호출 확인 및 결과 한 건 기록 | 후보 비교표, 두 모델의 기본 응답, 결과 한 건의 저장 확인, 평가 질문 초안 |
| 2일차 | 평가 질문/채점 기준 확정, 같은 조건에서 로컬 실험 | 모델별 원본 응답/설정/측정값/성공/오류 기록 |
| 3일차 | 품질 채점/실패 사례 분석, 소규모 Cloud 비교, 필요한 재실험 | Local–Cloud 비교와 선정 근거 초안 |
| 4일차 | 저장소/README 정리, 재실행 확인, 최종 발표 | 실험 근거가 연결된 최종 제출물 |

### 참여 및 제출 단위

프로젝트는 **개인 또는 팀**으로 수행합니다. 필수 실험과 제출 기준은 개인 수행자는 개인별로, 팀 수행자는 팀별로 적용합니다. 로컬 모델 2개 × 질문 10개 × 각 2회의 기본 실험 40회와 Cloud 모델 1개 × 공통 질문 5개 × 각 1회의 실험을 수행하고, GitHub 저장소 하나에 모아 제출합니다. 로컬 워밍업은 모델당 1회이며 기본 실험과 구분합니다.

### 팀 참여자 안내

고정된 역할 분담은 필수가 아닙니다. 필요한 작업은 팀 상황에 맞게 나누되, 질문과 평가 기준 및 최종 선정은 함께 결정합니다. **모든 팀원은 모델 실행/결과 기록/채점에 참여**하고, 작업을 나눈 경우 README에 참여 내용을 간단히 남깁니다. 팀의 기본 실험 40회를 분담하는 것이며, 팀원 각자가 전체 실험을 중복 수행할 필요는 없습니다.

# STEP 2. 모델 요구사항 정의

문제가 정의되었다면 어떤 조건을 만족해야 사용할 수 있는지, 여러 후보가 조건을 만족하면 무엇을 우선할지 정합니다. 요구사항은 **필수 통과 조건**과 **선호 우선순위**로 나누어 작성합니다.

### 실험 전에 정할 선정 기준

- **필수 통과 조건:** 반드시 만족해야 하는 조건과 충족 여부를 확인할 방법을 적습니다. 수업용 노트북에서의 실행 가능 여부, 사용 목적에 맞는 License, 필요한 입력과 출력 길이의 수용 여부, 태스크에 필요한 최소 품질 등을 Use Case에 맞게 정합니다.
- **선호 우선순위:** 필수 조건을 충족한 후보 사이에서 무엇을 우선할지 정합니다. 품질, 전체 응답 시간, 메모리 사용량 등의 우선순위를 적고, 결과가 엇갈릴 때 어떤 기준을 먼저 적용할지 설명합니다. 복잡한 가중치표는 필수가 아닙니다.
- **확정 시점:** STEP 5에서 질문과 품질 채점 기준을 정할 때 판정 방법을 구체화하고, 본 실험 전에 확정합니다. 필요한 점수나 시간 기준은 개인 또는 팀이 정하고 두 로컬 후보에 동일하게 적용합니다.

### 요구사항 검토에 활용할 모델/실행 정보 예시

| 항목 | 확인할 정보 |
| --- | --- |
| Language | Korean |
| Model Size | 수업용 노트북에서 실행 가능한 후보 중 선정 |
| License | Commercial Use 가능 |
| Context Length | 사용할 입력 문서와 출력 길이를 수용할 수 있는 범위 |
| GPU | 실제 GPU/VRAM과 CPU/GPU 적재 상태 확인 |
| Task | Chat / QA |

위 정보를 조사하는 데서 그치지 않고, 정한 필수 조건을 충족하는지 판단합니다. STEP 8에서는 **필수 조건별 충족 여부를 먼저 확인하고, 조건을 충족한 후보에 선호 우선순위를 적용**해 선정 이유를 설명합니다.

# STEP 5. 평가 질문과 품질 기준 확정

선정한 Use Case에 맞는 **고정 질문 세트 10개**를 만들고 모든 로컬 후보에 동일하게 적용합니다. 추가 질문은 선택이며 기본 10개의 집계와 구분합니다. 질문마다 ID, 입력 자료, 기대 결과 또는 확인할 항목을 기록합니다.

### 질문 구성

- 대표적인 정상 사례
- 조건이 애매하거나 판단이 어려운 경계 사례
- 정보가 부족하거나 요청 범위를 벗어난 사례

요약/문서 QA에서는 같은 원문을 함께 제공합니다. 긴 문맥 실험은 정의한 요구사항에 필요한 경우에만 포함하고, 비교 모델이 처리할 수 있는 범위로 맞춥니다.

### 품질 평가 기준

실험 전에 태스크에 맞는 항목과 점수 기준을 정합니다. 예를 들어 정확성, 핵심 정보 누락, 지시/형식 준수, 한국어 표현, 정보 부족 시 대응을 평가할 수 있습니다.

점수만 적지 말고 **응답의 어느 부분이 기준을 충족하거나 위반했는지** 근거를 함께 남깁니다. 정답이 있는 항목은 정답과 비교하고, 판단이 필요한 항목은 개인 수행 시 같은 기준으로 다시 검토하고, 팀 수행 시 팀원이 같은 기준으로 교차 확인합니다.

### 통제할 조건

동일한 질문/지시문/대화 이력 처리/출력 한도를 적용하고 생성 설정을 기록합니다. 독립 질문은 이전 질문의 대화 이력을 이어 붙이지 않습니다. 모델별 필수 입력 형식이나 지원 설정이 달라 완전히 맞출 수 없는 부분은 차이를 명시합니다.

모델 비교 중 특정 모델에만 유리하게 프롬프트를 바꾼 결과는 기본 비교와 분리합니다. Cloud 비교에 사용할 질문 5개도 결과를 보기 전에 이 세트에서 선정합니다.

# STEP 6. 로컬 모델 품질/성능 측정

**로컬 모델 2개 × 질문 10개 × 질문별 2회**를 기본 실험으로 수행합니다. 모델당 워밍업 호출을 1회 실행하고, 그 기록은 본 비교 집계에서 분리합니다. 반복 실행의 차이와 실패도 기록합니다. 질문별 2회 결과를 모두 남기고, 수치 지표는 두 측정값과 평균을 함께 확인합니다. 실패한 회차는 유효 측정값과 구분하며 누락된 값을 0으로 채우지 않습니다.

### Quality

STEP 5에서 확정한 기준으로 원본 응답을 평가합니다. 평균 점수와 함께 대표적인 성공/실패 사례를 제시합니다. 호출 실패는 품질 점수와 별도로 기록하며, 실패 기록을 지우거나 성공 응답으로 대체하지 않습니다.

### 평균과 함께 표시할 집계 정보

- **호출 성공 수 / 전체 시도 수:** 기본 실험을 모델별로 집계합니다. 계획된 본 실험은 모델당 20회이며, 호출 실패도 전체 시도 수에 포함합니다. 호출 성공과 답변 품질의 통과 여부는 구분합니다.
- **지표별 집계 응답 수(n):** 품질 점수와 각 성능 지표의 평균 옆에 계산에 사용한 응답 수를 표시합니다. 정상적으로 받은 낮은 품질의 응답도 채점에 포함합니다. 측정값을 얻지 못한 경우에는 해당 지표의 평균과 n에서 제외하고 사유를 남깁니다. 유효한 값이 한 건도 없으면 평균을 0으로 표시하지 않고 집계 불가로 표시합니다.
- **집계 범위:** 기본 비교표에는 본 실험의 유효 결과를 사용합니다. 워밍업, 재시도, 추가 실험은 별도로 기록/집계하며, 원래 실패 기록을 재시도 성공 결과로 덮어쓰지 않습니다.
- **해석:** 평균과 함께 성공 수, 전체 시도 수, 지표별 n을 확인합니다. 모델별 집계 응답 수나 포함된 질문 범위가 다르면 차이를 밝히고 최종 선정에 반영합니다.

### Performance

2번 예제의 `response`는 한 질문의 최종 응답입니다. 답변 외에 로딩 시간과 토큰 통계도 이 객체에서 확인할 수 있습니다. VRAM과 실행 설정은 같은 예제의 `client.ps()`로 조회한 **현재 실행 모델 목록**에서, 실험한 모델 태그와 일치하는 항목을 확인합니다.

| 항목 | 확인 위치/단위/측정 시점 |
| --- | --- |
| 전체 응답 시간 | 2번의 `elapsed` 값(초). 요청 직전부터 최종 응답 수신 직후까지 측정합니다. 모든 후보에 같은 응답 수신 방식을 사용합니다. |
| 모델 로딩 시간 | 최종 응답의 `response.load_duration`. 나노초 값을 1,000,000,000으로 나누어 초로 기록합니다. 워밍업과 본 실험의 값을 구분합니다. |
| 토큰 생성 속도 | 같은 최종 응답의 `response.eval_count`(생성 토큰 수)와 `response.eval_duration`(생성 구간의 나노초). `eval_count / (eval_duration / 1_000_000_000)`으로 tokens/s를 계산하고, 출력 토큰 수도 함께 기록합니다. 전체 응답 시간과는 다른 지표입니다. |
| VRAM | `client.ps()`의 모델 목록에서 해당 모델의 `size_vram`(바이트)을 확인합니다. 각 답변을 받은 직후, 모델을 메모리에서 내리기 전에 조회하고 관측 시점을 기록합니다. 바이트를 1,048,576으로 나누면 MiB입니다. 이는 해당 시점의 값이며 최대 VRAM 측정값은 아닙니다. GPU가 없거나 측정할 수 없으면 사유와 함께 해당 없음/측정 불가로 표기합니다. |
| 실행 조건 | 같은 실행 모델 정보의 태그/`digest`(식별값)/`details.quantization_level`(양자화)/`context_length`(실제 Context 토큰 수)를 확인합니다. 요청 코드의 출력 한도/생성 설정, `ollama ps`의 CPU/GPU 적재 상태, 실행 환경도 함께 기록합니다. Model Card의 최대 Context와 실제 실행 Context는 구분합니다. |

통계 필드가 없거나 `eval_duration`이 0 이하이면 생성 속도를 계산하지 않고 사유를 남깁니다. 실행 모델 목록이 비어 있다면 모델이 이미 메모리에서 내려갔는지 확인합니다. 확인하지 못한 값을 0으로 채우지 않습니다.

양자화 태그는 실행한 가중치의 표현 방식을 구분하는 정보입니다. 사용한 버전은 기록하되, 양자화 버전 간 비교는 선택 실습에서 다룹니다.

### 측정 예제를 프로젝트에 적용하는 방법

- **제공된 출발점:** 2번의 `03_measure_time.py`로 전체 응답 시간을 측정합니다. 같은 모델/질문/출력 한도로 호출하는지 먼저 확인합니다.
- **개인 또는 팀이 확장할 부분:** 위 표의 로딩 시간/출력 토큰 수/생성 속도/VRAM/실행 조건을 확인하고 기록합니다. 이 항목들은 프로젝트의 필수 기록 범위이며, 현재 예제에 모두 출력되어 있지는 않습니다. 위 표에서 확인할 필드와 단위를 찾아 측정/저장 부분을 구성합니다.
- **반복과 기록:** 모델당 워밍업 1회와 질문별 본 실험 2회를 구분합니다. 질문을 한 건씩 실행하거나 반복 코드를 작성할 수 있으며, 어느 방식이든 모든 회차의 원본 응답/측정값/실패 기록을 남깁니다.

### 비교할 때 주의할 점

- 모델마다 같은 PC/같은 실행 조건을 사용하고, 다른 PC의 절대 속도를 합쳐 모델 순위를 매기지 않습니다.
- 첫 실행의 로딩 지연과 로드된 상태의 응답 지연을 구분합니다.
- 토큰화 방식이 다를 수 있으므로 tokens/sec만으로 품질이나 사용자 체감 속도를 판단하지 않습니다.
- Ollama의 시간 통계는 나노초 단위입니다. 사용한 변환과 계산 기준을 기록합니다.
- ollama ps의 PROCESSOR는 CPU/GPU 적재 상태입니다. GPU 이용률이나 VRAM 용량 자체가 아닙니다. 실행 모델의 size_vram도 측정 시점의 값으로 기록하며, 별도 측정 없이 최대 VRAM이라고 표시하지 않습니다.
- 기본 실험은 응답을 모두 받은 뒤 평가합니다. 첫 토큰 지연시간을 별도로 측정하지 않았다면 전체 응답 시간을 TTFT로 표기하지 않습니다.

# 선택 실습 A. Quantization 비교

기본 과제에서는 양자화의 목적을 이해하고 사용한 버전을 기록합니다. 직접 비교 실험은 선택입니다.

수행하는 개인 또는 팀은 **같은 모델의 양자화 버전 2개**를 골라 질문/설정/실행 조건을 맞춥니다. 서로 다른 모델의 차이를 양자화의 효과로 해석하지 않습니다.

### 비교 예시

- FP16
- 8bit
- 4bit

확인해야 할 질문

> 모델을 Quantization하면 VRAM 사용량은 얼마나 감소하는가?
> 

> 속도에는 어떤 차이가 발생하는가?
> 

> 모델 품질에는 어떤 변화가 생기는가?
> 

FP16/8bit/4bit를 모두 실행할 필요는 없습니다. 수업용 노트북에서 실행 가능한 조합을 확인한 뒤 선택하고, 속도/메모리/품질의 변화는 실제 관측 결과에 근거해 설명합니다.

# 선택 실습 B. Embedding 실험

후속 검색/RAG 학습을 위한 선택 실습입니다. 기본 모델 선정 과제의 필수 결과에 포함하지 않습니다.

Sentence Transformers를 활용하여 문장을 Embedding Vector로 변환합니다.

### 흐름

Sentence → Embedding Vector → Cosine Similarity → Semantic Similarity

### 예시 문장

- 고양이가 소파 위에 있다.
- 소파 위에 고양이가 앉아 있다.
- 오늘 주식시장이 상승했다.

Embedding을 통해 의미가 비슷한 문장이 Vector Space에서도 가까운 위치를 가지는지 확인합니다.

이 경험은 이후 학습하게 될 다음 과정의 기초가 됩니다.

> Embedding → Vector DB → Retrieval → RAG
> 

생성 모델의 토큰 ID/내부 토큰 표현과 문장 비교용 임베딩을 구분합니다. 같은 임베딩 모델과 설정으로 얻은 벡터끼리 비교하며, 유사도 값을 답변의 사실성 점수로 해석하지 않습니다. 이번 선택 실습에서도 Vector DB나 RAG 시스템 구현은 요구하지 않습니다.

# STEP 7. Open-source LLM vs Cloud API 비교

**Cloud API 모델 1개**에 STEP 5에서 미리 정한 공통 질문 5개를 각각 1회 적용하고, 로컬 모델의 동일 질문 2회 결과와 비교합니다. 로컬은 2회, Cloud는 1회라는 반복 수를 표시하고 로컬의 좋은 결과 한 건만 골라 비교하지 않습니다. 응답 시간에는 각 실행 환경과 네트워크 조건의 영향이 포함됨을 함께 설명합니다. 추가 호출/반복은 필요성을 확인하고 기본 비교와 구분해 기록합니다.

Cloud 결과는 로컬 후보를 고를 때 참고할 비교 기준입니다. 최종 로컬 모델 선정과 실제 서비스의 Local–Cloud 운영 방식 권고는 구분해 작성합니다.

2번의 `02_luna_chat.py`를 Cloud 호출의 출발점으로 사용합니다. 개인 또는 팀은 미리 정한 질문 5개에 맞게 입력을 바꾸고, 응답/성공/오류 상태/입력/출력 토큰 사용량을 기록하는 부분을 추가합니다. Cloud의 전체 응답 시간은 2번의 시간 측정 원리를 API 요청 전후에 적용합니다.

### API 사용량과 비용 기록

- 사용할 모델과 실제 단가를 확인하고, 호출별 입력/출력 토큰 사용량과 예상 비용을 기록합니다. 비용은 기록한 사용량과 단가로 직접 계산하거나 코드로 계산할 수 있습니다.
- 실행 전후 OpenAI API 사용량에서 실제 사용 내역도 확인합니다. 사용량과 단가로 계산한 추정 비용과 실제 사용 내역을 구분합니다.
- 2번 예제는 실행 후 터미널에서 API 키를 화면에 표시하지 않고 입력받습니다. 입력한 키는 코드 파일/저장소/실험 로그/스크린샷에 포함하지 않습니다. 공개/가상 데이터만 사용합니다.

### 주요 비교 기준

공통 질문 5개의 기본 결과를 집계할 때도 STEP 6과 같이 호출 성공 수/전체 시도 수와 지표별 집계 응답 수(n)를 함께 표시합니다. 이 비교의 계획된 본 실험 수는 로컬 후보마다 10회, Cloud 모델은 5회입니다.

| 기준 | Local LLM | Cloud API |
| --- | --- | --- |
| Quality |  |  |
| Latency |  |  |
| Cost |  |  |
| Security |  |  |
| Infrastructure |  |  |
| Customization |  |  |
| Operations |  |  |

품질/응답 시간/토큰 사용량은 **실측 결과**, 데이터 통제/인프라/운영 부담은 **서비스 요구사항과 확인한 조건에 따른 분석**으로 구분합니다. 로컬 운영에도 장비/전력/관리 비용이 있으므로 호출 요금이 없다는 이유만으로 총비용을 0원으로 표기하지 않습니다.

Local/Cloud는 실행 위치에 관한 구분이고, 공개 가중치/License는 모델 이용 조건에 관한 구분입니다. 실제 실행 위치와 이용 조건을 각각 확인합니다.

# STEP 8. 최종 모델 선정 및 발표

마지막 단계에서는 비교한 **로컬 후보 중 프로젝트 Use Case에 가장 적합한 모델 1개**를 선정합니다. Cloud 모델이 더 높은 품질을 보였더라도 그 결과를 그대로 기록하고, 로컬 후보의 선택 이유와 실제 서비스의 운영 방식 권고를 따로 설명합니다. 두 로컬 후보 모두 핵심 요구사항을 충족하지 못하면 그 사실을 명시하고, 상대적으로 적합한 후보와 실제 도입 가능 여부를 구분합니다.

STEP 2에서 정한 필수 통과 조건별로 두 후보의 충족 여부와 실험 근거를 정리하고, 조건을 충족한 후보에 선호 우선순위를 적용합니다. 호출 성공 수/전체 시도 수와 지표별 집계 응답 수도 선정 근거에 함께 반영합니다.

### 발표 예시

> Model A가 가장 높은 Benchmark 점수를 기록했지만, 우리 서비스에서는 Model B를 선택했습니다.
> 
> 
> Model B는 Model A와 비교했을 때 품질 차이가 크지 않으면서 VRAM 사용량이 적고 응답 속도가 빠릅니다.
> 
> 또한 상업적 사용이 가능한 License를 가지고 있어 현재 서비스 환경에 더 적합하다고 판단했습니다.
